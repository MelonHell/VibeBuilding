# Blockwright — конфигурация Claude для этого проекта

Скиллы, команды и агент фото-ревьюера, которые ведут сборку зданий Minecraft.
**Движок живёт в проекте, а не здесь:**

```
blockwright/          библиотека
tools/                отдельные CLI
docs/                 sources.md, pipeline.md, data-contract.md
buildings/            по пакету на здание
    _template/        скелет, из которого заводят новое
.claude/              вот эта конфигурация: скиллы, команды, агент
```

Так и задумано. Здания импортируют `blockwright` абсолютно и запускаются как
модули из корня проекта, поэтому библиотека должна лежать в корне; а `.claude/`
остаётся тем, чем является, — набором инструкций, которые правят, не трогая код.

Собирается что угодно и из чего угодно: словесное описание, чертежи, векторный
план, полноценная 3D-модель, захват из Google Earth, фотографии, плоская карта.
Реальный дом, здание из игры, объект по эскизу — разницы нет. Меняется только то,
чем измерено и чем проверено.

## Что нужно

- **Python 3.11+** и **Pillow** (`pip install pillow`). Всё остальное — голая
  стандартная библиотека: NBT и схематики читаются и пишутся ей. Pillow
  импортируется лениво, внутри функций, поэтому его отсутствие всплывает не при
  импорте, а на первом же обмере.
- **numpy — необязателен.** Если он есть, часть операций над масками идёт
  быстрее; если нет, работает всё то же самое. Обе реализации обязаны выдавать
  **побайтово одинаковый** результат, и `python -m tools.mask_selftest` это
  проверяет — иначе пороги, откалиброванные на числах этого кода, поехали бы
  молча.
- **Blender** в PATH — для конвертации Google Earth и рендеров эталона. Без него
  постройка собирается и гейт работает, а листы сравнения и половина фото-ревью
  нет. На Windows обычно не в PATH.

## Как завести здание

```
/blockwright-new <имя_здания>      пакет из buildings/_template
```

Положить в `buildings/<имя>/input/` то, что есть. Обязательных файлов нет;
обязательно, чтобы был хоть один вход и чтобы кто-то отвечал на вопрос плана:

```
input/
    brief.md          словесное описание — иногда этого одного хватает
    plan.geojson      контур: OSM-экспорт, GIS, CAD (или plan.svg)
    layout.png        кроп плоской карты, 1 пиксель = 1 метр
    layout.schem      тот же кроп схематикой, для посадки в мир
    drawings/         чертежи с масштабом
    sketches/         эскизы и чертежи без масштаба
    model.obj         полноценная 3D-модель: метры, Y вверх
    ge-export/        пакет сценария из Google Earth
    photos/           все фотографии, какие есть
```

И прогнать:

```
/blockwright-run <имя_здания>      обмер, чертёж, гейт
/blockwright-review <имя_здания>   рендеры и фото-ревью
```

Командами не обязательно: скиллы поднимаются и по обычной просьбе — «построй
здание по этой карте», «собери вот эту модель в майне», «прогони гейт»,
«посмотри на рендеры».

Вручную то же самое:

```sh
python -m buildings.<имя>.probes.derive
python -m buildings.<имя>.build
python -m buildings.<имя>.gate
python -m buildings.<имя>.review --mesh
```

## Что внутри

```
.claude/
    settings.json                 разрешения на запуск скриптов пайплайна
    skills/
        blockwright/                 корневой: три правила, карта стадий
        blockwright-capture/         стадия 1 — захват и конвертация
        blockwright-measure/         стадия 2 — обмер плана
        blockwright-schedule/        стадия 3 — обмер разреза и манифест
        blockwright-draw/            стадия 4 — чертёж
        blockwright-gate/            стадия 5 — числа: гейт, отчёт, листы
        blockwright-review/          стадия 5 — глаза: фото-ревью
    commands/
        blockwright-new.md           завести здание из скелета
        blockwright-run.md           обмер, чертёж, гейт
        blockwright-review.md        рендеры и фото-ревью
    agents/
        blockwright-photo-reviewer.md   наивный ревьюер: только картинки
```

`buildings/_template/` — рабочий скелет: он запускается и собирает объёмный
этюд, ничего не зная о конкретном здании и не зная заранее, какие входы ему
дадут. Всё специфическое в нём — помеченные таблицы (`DECLARED_PLAN`,
`DECLARED_HEIGHTS`, `DECLARED_STOREY`, `STRIPS`, `DISCS`, `MODEL_PARTS`,
`MAP_PALETTE`, `VECTOR_SCALE`, `DECLARED`, `COUNTS`, `LEVELS`, `RINGS`,
`windows()`, `DESCRIPTION`, `PLAN`) и помеченные блоки комментариев.

Аппаратура, которая иначе копировалась бы в каждое здание — чтение входов и
фото-ревью, — живёт в `blockwright.survey` и `blockwright.reviewing`:
скопированный драйвер гниёт в каждой копии по-своему, и копии продолжают
печатать зелёное.

## Как это работает, в трёх правилах

**Один блок — один метр**, и один пиксель плоской карты — один метр. Никаких
масштабных коэффициентов нигде.

**Каждый вход решает только то, в чём он силён.** Векторный план — посадку и
контур точно, без палитр и сглаживания. Карта — то же самое, но рисунком.
3D-модель — ещё и форму. Захват Google Earth — объём и высоты, и никогда форму.
Фотографии — материал, цвет, ритм и то, какие части существуют, и никогда
размеры. Описание и эскиз — всё то же самое, но объявлениями, с указанием
источника у каждого числа. Полная таблица — `docs/sources.md`.

**Постройка проверяется тем входом, которого ей не давали.** Сравнение результата
с картой, из которой он выведен, доказывает только что растеризатор работает.
Поэтому гейт режет сечения по эталонной геометрии, а фото-ревьюеру дают картинки
и больше ничего. Когда свидетеля нет — когда всё пришло из одного файла или всё
объявлено словами, — гейт печатает `ungraded`, а не `pass`. Это честный исход, а
не поломка.

Подробности и обоснования — в `docs/pipeline.md`.
