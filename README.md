# Blockwright

Инструменты для сборки зданий в Minecraft, по одному зданию за раз.

Здание собирается из того, что есть: словесного описания, чертежей, векторного
плана, полноценной 3D-модели, захвата Google Earth, фотографий, кропа плоской
карты — в любом сочетании. На выходе схематика с верным пятном застройки, верным
углом, верными высотами и главными объёмами. Дальше её берут живые строители.

Это не попытка генерировать законченные здания. Это измерительно-чертёжный
набор: он снимает ту часть работы, которая является арифметикой, и оставляет ту,
которая является решением.

## Раскладка

```
blockwright/          библиотека: схематики, маски, рамы, меши, примитивы блоков,
                      модель входных данных, дорожная сеть плоской карты,
                      аппаратура обмера и фото-ревью
tools/                отдельные CLI: конвертация Google Earth, рендеры Blender,
                      самопроверки, синтетическое здание для тестов
buildings/            по пакету на здание — свои входы, рецепт и проверки
    _template/        скелет, из которого заводят новое здание
docs/                 как устроен пайплайн и что лежит в папке здания
.claude/              скиллы, команды и агент, которые ведут сборку
```

## Запуск

Скрипты импортируют `blockwright` абсолютно и запускаются как модули из этого
каталога, поэтому от текущей директории не зависит ничего:

```sh
python -m buildings.<имя>.probes.derive     # обмерить входы
python -m buildings.<имя>.build             # начертить здание
python -m buildings.<имя>.gate              # сверить с эталоном
python -m buildings.<имя>.review --mesh     # и посмотреть на это
```

Именно в таком порядке. Чертёж читает то, что намерил обмер, и без этого файла
не стартует — поэтому ни одна константа в скрипте здания не может продолжать
говорить то, что было верно до перерисовки карты. Ревью отказывается работать
против схематики старше рецепта; папку, которую оно оставляет в `out/review/`,
читает модель в сессии, и находки возвращаются туда же.

Пути к данным разрешаются из `paths.py` каждого здания, так что текущий каталог
важен только импортам.

Нужен Python 3.11+ и Pillow. numpy необязателен и только ускоряет — обе
реализации обязаны давать побайтово одинаковый результат. Blender нужен для
конвертации Google Earth и рендеров эталона.

Самопроверки, которые стоит прогонять после любой правки библиотеки:

```sh
python -m tools.pipeline_selftest     # все четыре ветки входов, от обмера до гейта
python -m tools.schedule_selftest     # манифест видит все режимы отказа
python -m tools.mask_selftest         # быстрый путь совпадает с обычным
python -m tools.fixture buildings/<имя>/input   # синтетическое здание целиком
```

Первая — главная. Она собирает синтетическое здание четырьмя способами (карта,
модель, описание, вектор), прогоняет каждый через `derive`, `build` и `gate` и
падает, если хоть одна строка гейта покраснела. Ветки ломаются именно так: правку
пишут против той, что под рукой, а остальные три продолжают «работать» ровно до
того дня, когда их кто-нибудь запустит.

## Три правила, из которых следует всё остальное

**Один блок — один метр**, и один пиксель плоской карты — один метр. Никаких
масштабных коэффициентов нигде.

**Каждый вход решает только то, в чём он силён.** Карта авторитетна для
положения, размера и поворота — и никогда для отдельного ребра, потому что она
рисована от руки. Захват Google Earth авторитетен для объёма — и никогда для
формы, потому что это фотограмметрия. Фотографии авторитетны для материала и
ритма — и никогда для размеров.

**Постройка проверяется тем входом, которого ей не давали.** Сравнение результата
с картой, из которой он выведен, доказывает только, что растеризатор работает.
Меш читается ради чисел и никогда ради геометрии — поэтому он и может быть
свидетелем. Когда свидетеля нет, гейт печатает `ungraded`, а не `pass`.

## Состояние

Пайплайн принимает семь видов входа в любом сочетании и проверен на пяти
сценариях: карта с захватом, только модель, только описание, только чертежи,
векторный план с захватом.

Не сделано: плагин для Paper (удалённые get/set блока через FAWE) и MCP-сервер,
который вёл бы всё это из чата, чтобы правки появлялись в живом мире, а не в
файле. Схематик достаточно, чтобы разрабатывать против них, и начинать стоило
именно с них.
